## Именование и константы

- Называй идентификаторы по сущности: `objectId`, `ticketId`, `cottageQueueId`; не называй идентификаторы заявок `objectIds`, а идентификатор объекта - `typeId`
- Функции `check...` и геттеры `is...`, `has...`, `can...` должны возвращать boolean. Загрузку называй `load...`, преобразование фильтра - `transformFilter...`, получение тела запроса - `getBody`, а функцию фильтрации - `getFiltered...`

- Размеры маркеров, пороги количества, лимиты и длительности выноси в именованные константы; подписи ограничений и проверки должны использовать одни значения
- В миграциях фиксируй числовое значение enum и указывай его источник комментарием; в прикладном коде и скриптах используй импорт enum
- Используй стабильные идентификаторы для сопоставления сущностей, выбора поведения и React-ключей; не привязывай логику к отображаемому названию

- Для сборки объекта без незаполненных необязательных полей используй `getFilledObject` из `@ecosystem/esoft-tools-shared` вместо набора условных spread; отдельно проверь, должны ли сохраняться ноль и `false` по контракту

## Простота и читаемость

- Проверяй условия выхода до запросов, создания моделей и вычислений, которые при этих условиях не нужны
- Уменьшай вложенность ранними возвратами; объединяй одинаковые условия и не дублируй ветки с одной логикой
- Если ключ известен, обращайся к `plugin[mainOfficeId]` и `cache[id]` напрямую; не используй для этого `Object.entries(...).find(...)`
- Для минимума и максимума используй `Math.min` и `Math.max` вместо собственного цикла сравнения или утилит `setMin`/`setMax` с побочными эффектами
- Не создавай промежуточные переменные, преобразования и функции, которые только передают значение дальше без дополнительного смысла
- Избегай лишних функций-обёрток. Передавай функцию напрямую, если обёртка не добавляет логики и не меняет поведение. Например, beforeEach(jest.clearAllMocks) вместо beforeEach(() => jest.clearAllMocks()), onClick={handleClick} вместо onClick={(event) => handleClick(event)}
- Удаляй проверки, optional chaining, приведения типов и значения по умолчанию, избыточность которых уже следует из контракта или предыдущего условия
- Сохраняй единое назначение функции во всех ветках; не совмещай под одним API создание нового запроса и изменение переданного запроса

## Данные, коллекции и пустые значения

- При преобразовании входных данных не используй delete, присваивание полей или изменение элементов исходного массива. Возвращай новый объект или массив. Мутация допустима, если изменение переданного значения - явное назначение функции
- Собирай результат обхода в возвращаемом значении или аккумуляторе; не изменяй внешние коллекции из `map` и `reduce`
- Для проверки существования используй `some`, а для получения одного элемента - `find`; не проходи весь массив через `filter`, если нужен только один результат
- Для сопоставления цен с объектами заранее строй `array2Object(prices, 'entityId')`, для восстановления порядка объектов - `array2Object(objects, 'id')`; не выполняй `prices.find(...)` или `objects.find(...)` для каждого элемента
- Выноси неизменные вычисления за пределы циклов; повторно используй уже полученные массивы и собирай связанные результаты за один проход, когда это упрощает код
- В локальном `reduce` добавляй элементы через `acc.push(...)`, а не возвращай каждый раз `acc.concat(...)` или `[...acc, ...]`; для обновления локального кэша записывай `cache[id] = result`, для удаления - `delete cache[id]`
- До обращения к результату `find` или первому элементу ответа проверь, что запись найдена. Для необязательной цены используй `pricesByObjectId[id] || {}` перед деструктуризацией; для ещё не загруженного каталога возвращай `catalogs.name || []`
- Выбирай проверку наличия по смыслу данных: различай допустимый ноль, `false`, пустую строку, `null` и `undefined`; используй `hasValue`, когда нужно исключить только `null` и `undefined`
- Сохраняй понятную форму состояния: отсутствие одиночной сущности обозначай `null`, коллекции - пустым массивом; не подменяй отсутствие сущности пустым объектом с отсутствующими обязательными полями

## Асинхронные операции

- Запускай независимые запросы параллельно через `Promise.all`; не выстраивай последовательные `await` без зависимости по данным
- Используй `Promise.allSettled` для независимых операций, где частичный успех допустим и ошибка одного элемента не должна скрывать результаты остальных
- Не включай необязательную загрузку полигонов, отправку метрик и уведомлений в ожидаемый `Promise.all` создания или удаления объекта; запускай их фоном через хук, событие либо отдельный промис с обработкой ошибки
- У фонового вызова добавляй `.catch(err => logger.error(toStr(err)))` или обрабатывай результаты `Promise.allSettled`; обрабатывай также отклонение `startParsing()`, а не только ошибки внутри его `.then(...)`
- Не запрашивай повторно данные, которые уже получены, доступны в текущем результате или корректно хранятся в кэше

## Контракты и спецификации API

- Описывай фактические типы и допустимые значения полей; не разрешай в схеме формы данных, которые реализация затем безусловно отвергает
- Для массива положительных идентификаторов используй `$ref: 'shared://ArrayOfPositiveInteger'`, для непустой строки - `shared://NotEmptyString`, для даты со временем - `shared://DateTime`; не заменяй их собственным описанием тех же типов
- Для типов объектов и сущностей используй ссылки на соответствующие enum, в том числе `enum://object/cottageType` и `enum://entity/type`, вместо вручную перечисленных числовых значений
- Указывай в описании поля используемый enum или название каталога; объясняй бизнес-смысл поля без необходимости читать задачу
- Для объектов с фиксированным набором полей задавай `additionalProperties: false`, включая вложенные объекты
- Для обязательного входного параметра задавай `required: true`, для обязательных полей объекта - список `required`, для допустимого `null` - `nullable: true`, для непустого массива - `minItems: 1`, для непустого фильтра-объекта - `minProperties: 1`; элементы массива описывай через `items`, а не `properties`
- Проверяй совместное наличие `entity` и `entityId`; набор сущностей передавай как `entities: [{entity, entityId}]`, а не как независимые массивы `entityTypes` и `entityIds` без связи между элементами
- Передавай массивы идентификаторов и объёмные наборы параметров в теле запроса, когда query-параметры могут превысить допустимый размер
- Описывай назначение метода через его результат и поведение; не привязывай описание общего метода к конкретному экрану или табу
- Повышай версию спецификации по характеру изменения совместимости; для совместимого расширения используй minor, для нарушения контракта - major

## SQL и производительность запросов

- Используй Knex для обычных выборок, фильтров и обновлений; оставляй raw SQL для выражений, которые им действительно удобнее описать
- В `pg.raw` и `whereRaw` передавай значения через `?`, идентификаторы таблиц и колонок - через `??`, либо используй именованные bindings `:value` и `:field:`; не вставляй эти параметры через `${...}` даже для значений, заданных кодом
- Группируй альтернативы через `model.andWhere(qb => qb.whereNotExists(...).orWhereExists(...))`, чтобы получилось `остальные фильтры AND (NOT EXISTS (...) OR EXISTS (...))`
- Добавляй `.whereNull('deletedAt')` и `.onNull('relations.deletedAt')` для активных записей и связей; перед `.update({deletedAt: getUtcDate()})` отсекай уже удалённые строки
- Для проверки наличия связи «один ко многим» используй `EXISTS`, когда данные связанной таблицы не нужны; не размножай строки основного запроса лишними JOIN
- Не добавляй `LIMIT` в подзапрос `EXISTS` без подтверждённой необходимости; удаляй JOIN, группировки и `DISTINCT`, которые больше не нужны запросу
- Передавай в `fields` только используемые поля; если нужны одни идентификаторы, используй `.pluck('id')` вместо `.select('id')` с последующим `map`; доступные категории ограничивай через `whereIn('category', availableCategories)` до получения данных
- В вызовах получения медиа задавай `fields` и `relationFilter: {providedRelationsOnly: true}`; не выгружай все relations каждого attachment, когда нужны связи только с запрошенными сущностями
- Не ставь `limit: 0` без оценки числа записей; если нужен один результат, задавай `limit: 1`, а при необходимости получить все учитывай неявный лимит метода, который может вернуть только первые 20 записей
- Чтение уже существующих записей выполняй одним `whereIn` перед циклом; для массовой записи используй пакетный `insert`/`batchInsert`, а для однотипных обновлений рассматривай существующий `bulkUpdate` вместо запросов на каждой итерации
- Подтверждай оптимизацию фактическим SQL и `EXPLAIN ANALYZE` до и после изменения на репрезентативных данных; прикладывай к задаче планы именно реализованной версии запроса
- Подбирай состав и порядок колонок индекса по реальным фильтрам и плану запроса; проверяй, не покрывает ли его уже существующий индекс

## Транзакции, миграции и индексы

- Чтения и обновления, составляющие одну атомарную операцию, выполняй через одну `trx`; не восстанавливай старые значения отдельным запросом в `catch` вместо транзакции
- Если обновление зависит от прочитанного предыдущего состояния строки, используй `.forUpdate()` внутри транзакции; одна транзакция без блокировки не гарантирует, что параллельное обновление не изменит это состояние
- Не удаляй аргумент `trx`, пока метод вызывается из другой транзакции; при ручном `const trx = await knex.transaction()` добавляй `await trx.rollback()` в обработку ошибки до коммита
- Не объединяй весь длительный пакетный скрипт в одну транзакцию без необходимости атомарности; учитывай длительность удержания блокировок
- Восстанавливай прежнюю схему и заменённые объекты в `down`, если миграция меняет или удаляет их
- Выноси массовое изменение существующих данных в отдельный скрипт вместо выполнения в миграции схемы
- Для индексов на рабочих таблицах используй `CREATE INDEX CONCURRENTLY` и `DROP INDEX CONCURRENTLY`; в такой миграции задавай `exports.config = {transaction: false}`. Если конкурентных операций нет, не отключай транзакцию без причины
- При замене индекса сначала создавай новый, затем удаляй старый; длительное построение планируй заранее через отдельную задачу на DevOps(сообщи мне об этом)
- Называй индексы и миграции по изменяемой таблице, колонкам и назначению; соблюдай кавычки для SQL-идентификаторов с camelCase
- Используй `hasTable` и `createTable` вместо устаревшего `createTableIfNotExists`

## Скрипты обработки данных

- До массового обновления или удаления оценивай число затрагиваемых записей; обрабатывай большие объёмы партиями с паузами, учитывая триггеры и репликацию
- Если скрипт уже обрабатывает записи партиями, добавляй `await delay(BATCH_DELAY)` между партиями; малое текущее число записей не отменяет паузу в предусмотренной пакетной обработке
- При обработке по `id` используй согласованные `.where('id', '>', cursor)` и `.orderBy('id')`; логируй последний обработанный идентификатор и принимай стартовый курсор из переменной окружения
- Выноси параметры запуска, которые могут меняться между повторными запусками, в переменные окружения или предусмотренные параметры скрипта
- Создавай таблицы резервных данных миграциями; сохраняй резервные данные после выполнения скрипта и различай запуски или окружения, если они используют общую таблицу
- Описывай команды `migrate:up` и `migrate:down` в конфигурации скрипта; добавляй инструкцию по запуску и доступным параметрам
- Логируй фактическое число изменённых записей после каждой партии и общий итог, используя результат `update`/`delete`, а не размер выбранной партии
- Перед ранним `return` из скрипта логируй причину остановки или пропуска с именем отсутствующего каталога или поля; не завершай скрипт молча
- Проверяй, что ранний `return` из-за отсутствия одного поля не пропускает изменение другого поля, которое по задаче должно выполняться независимо; зависимость между этими действиями должна быть явной
- Перед удалением или обновлением через `.first()` проверяй, что требуется обработать именно одну запись. Если нужно обработать все совпадения, не ограничивайся первым найденным полем

## React и MobX

- Пиши новые простые компоненты функциональными; при несложной доработке затронутого классового компонента переводи его на функциональный
- Для условного рендера по числу используй `!!count && <Component />` или `count ? <Component /> : null`; не пиши `count && <Component />`
- Если проп принимает строку, не передавай в него `false` через `condition && text`; используй `condition ? text : undefined`. В boolean-проп `isDanger` передавай boolean, а не строку `'danger'`
- Используй `useRef` или `React.createRef` для привязки к DOM; ищи якорь онбординга через `ref.current.querySelector('[data-...]')`, а не через глобальный `getElementById` или объект `{current: null}`, созданный вручную
- Однократную загрузку каталога и присвоение внешнему стору переноси в `useEffect(..., [])`; не выполняй их в теле рендера и не дублируй проверку загрузки, которую уже делает `CatalogsStore.loadCatalogs`
- Не создавай сторы и не запускай загрузку для компонента, который по условиям доступа или отображения не должен монтироваться
- Изменяй observable-состояние через `action` или `runInAction`; вычисляемые реактивные значения оформляй как `computed`
- Для компонента, который получает только обычные пропсы и стили, используй `magic(Component, {styles: s, withObserver: false})`; служебное поле, не участвующее в реактивном отображении, не объявляй `observable`
- Для состояния асинхронной загрузки используй существующий `DataLoadingState` из `@stores/components/shared/DataLoadingState`; обращайся к `.isLoading` и `.success()` вместо повторения сравнений со статусом и ручного объявления такого же состояния через `observable` и `action`
- Освобождай сторы, реакции и подписки при завершении их жизненного цикла; удаление ссылки на стор не заменяет dispose
- Не добавляй скрытые изменения других стор в общий сеттер; размещай координацию действий в вызывающем коде или предназначенном для этого обработчике

## Стили и локализация

- Подключай условные стили через `cn(s.base, {[s.active]: isActive})`; фиксированные отступы, рамки и варианты фона описывай в SCSS, а не в `style={{...}}`
- Используй существующие токены и палитру для цветов и оформления; не добавляй ссылки на несуществующие токены и не дублируй стили, уже задаваемые вариантом компонента
- Не используй `!important` для обхода ограничений общего компонента; проверь его API, значения по умолчанию и возможность задать размер внешней обёрткой
- Оборачивай HTML-разметку в `l10n`, если она написана на русском
- Выноси динамические значения за пределы переводимого текста; разделяй самостоятельные фразы и разделители на отдельные переводимые части

## Логирование, комментарии и проверка изменений

- Вместо `console.log(err)` и интерполяции `${err}` или `${body}` используй `logger.error(toStr(err))` и `toStr(body)` из `@ecosystem/esoft-tools-shared`, чтобы не получать `[object Object]`
- Указывай в сообщении лога фактически выполняемую операцию и причину ошибки; убирай отладочный вывод, повтор входных данных и избыточные сообщения на каждой итерации
- Вместо отдельных счётчиков успехов и ошибок используй один счётчик с меткой статуса; причины отключения соединения различай меткой причины. Не увеличивай метрику `invalid_response` при успешном ответе
- Объясняй комментариями причины неочевидных преобразований, ограничений и обходных решений; обновляй описание при изменении поведения
- Для глубоких импортов используй `@lib`, `@components`, `@stores`, `@utils` вместо цепочек `../../..`; внешние зависимости размещай перед локальными импортами, основной импорт SCSS называй `s`, если импортируется еще, то `ss` и так далее
- Строковые JSX-пропсы оформляй через выражение `variant={'body14'}`, а не `variant='body14'`; не задавай проп повторно, если компонент уже имеет нужное значение по умолчанию
- Не отключай линтер ради форматирования, которое можно исправить; проверяй lint и обязательные проверки pipeline перед передачей MR на ревью
- Проверяй новую логику тестами; для изменений под feature flag проверяй оба состояния флага и соответствие моков обоим контрактам
- Удаляй ставшие ненужными импорты, функции, стили и комментарии; не оставляй случайные изменения и коммиты другой задачи в MR
- Добавляй комментарии к регулярным выражениям
